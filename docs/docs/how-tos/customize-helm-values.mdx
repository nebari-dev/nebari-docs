NKP's foundational software (Envoy Gateway, cert-manager, Keycloak, and the rest) is installed from Helm charts with values that `nic` generates. Sometimes you need to change one of those values: raise a memory limit, add a service annotation your cloud load balancer needs, or turn on a chart feature.

You do that by committing an **overlay** file to your GitOps repository. ArgoCD picks it up on its next sync. You do not edit the generated manifests, and you do not re-run `nic`.

:::note[Do you have this?]
Look for a `values/` directory in your GitOps repository, under your `git_repository.path` if you set one. If it is there, you have overlays. If not, your cluster predates the feature; re-deploy with a newer `nic` to adopt the layout.
:::

## Why not just edit the manifests

Your GitOps repository has an `apps/` directory holding one ArgoCD Application manifest per component. Those files are **generated**. Every `nic deploy --regen-apps` rewrites them, so anything you hand-edit there is silently lost the next time someone deploys.

Overlays exist so your changes live in files `nic` never touches.

## The layout

Each component's values live in two places:

```
<git_repository.path>/
└── values/
    └── envoy-gateway/
        ├── base.yaml              # generated by nic — do not edit
        └── overlays/
            └── 30-my-change.yaml  # yours
```

- **`base.yaml`** belongs to `nic`. It is rewritten on every `nic deploy --regen-apps`. Treat it as read-only.
- **`overlays/*.yaml`** belongs to you. `nic` never writes to or deletes from this directory, so your files survive every deploy.

Overlays are available for the Helm-based foundational components: `envoy-gateway`, `cert-manager`, `keycloak`, `postgresql`, `cloudnative-pg`, `opentelemetry-collector`, `nebari-landingpage`, and, on providers that use them, `metallb` and `trust-manager`.

A component's `values/<app>/` directory only exists if that component is enabled for your provider. MetalLB, for example, is only used on some providers, so `values/metallb/` is absent elsewhere.

:::note[Raw-manifest components are not covered]
Some foundational pieces are plain Kubernetes manifests rather than Helm charts, and they have no overlay mechanism. If the component has no `values/<app>/` directory, there is nothing to override this way.
:::

## Add an overlay

Suppose Envoy Gateway needs two replicas instead of one.

**1. Find the key you want to change.** Read `values/envoy-gateway/base.yaml` to see what `nic` already sets, and check the chart's own documentation for keys it does not set. Your overlay uses the same key paths the chart expects.

**2. Write only the keys you are changing.** An overlay is not a copy of `base.yaml`; it is a patch on top of it.

```yaml title="values/envoy-gateway/overlays/30-replicas.yaml"
deployment:
  replicas: 2
```

**3. Commit and push.**

```bash
git add values/envoy-gateway/overlays/30-replicas.yaml
git commit -m "Raise Envoy Gateway to two replicas"
git push
```

That is the whole procedure. ArgoCD notices the commit and applies the change, typically within a minute or so. No `nic deploy` is required.

:::warning[The file must be committed]
ArgoCD reads committed content from your repository, never your local working copy. An overlay file that exists on your laptop but has not been pushed has no effect at all.
:::

## Ordering and merge rules

**Files apply in filename order, and the last one wins.** Prefix your filenames with a number (`30-replicas.yaml`) so precedence is obvious from a directory listing. This matters when a Software Pack ships an overlay and you want yours to win: give yours a higher number.

**Maps merge, lists are replaced.** If you set one key inside a map, the other keys in that map survive. But if you set a list-valued field, your list replaces the whole thing rather than adding to it. There is no way to append a single item to a list through an overlay.

**Namespace your keys when contributing to a shared map.** If several packs write entries into the same map, use a key like `<kind>/<packname>` (for example `otlp/langfuse`) so two packs do not overwrite each other.

## Verify it worked

Check the live resource first. For the replica example:

```bash
kubectl -n envoy-gateway-system get deployment envoy-gateway -o jsonpath='{.spec.replicas}{"\n"}'
```

If the value did not change, ask ArgoCD which files it actually used:

```bash
kubectl -n argocd logs deploy/argocd-repo-server -c repo-server \
  | grep "resolved value files" | grep envoy-gateway | tail -2
```

You want two paths: `base.yaml` and your overlay. Seeing only `base.yaml` means your overlay was not picked up; see below.

## If your overlay has no effect

Work through these in order.

**Is it committed and pushed?** The most common cause. Confirm the file is present on the branch ArgoCD tracks, not just locally.

**Is it in the right place?** The path is `<git_repository.path>/values/<app>/overlays/<name>.yaml`, and the filename must end in `.yaml`. A `.yml` extension is not matched.

**Is ArgoCD new enough?** Overlays need ArgoCD 3.4 or later. On older versions your overlay is ignored silently: the component stays Synced and Healthy, and nothing is logged. Check the component that does the work, not the ArgoCD UI or `argocd version`, both of which report a different component's version:

```bash
kubectl -n argocd logs deploy/argocd-repo-server -c repo-server | grep -c "resolved value files"
```

A count of zero means your ArgoCD predates 3.4. Recent `nic` releases install a new enough version, so this normally only appears on a cluster whose ArgoCD was installed by an older `nic`.

**Did you just upgrade ArgoCD?** An upgrade on its own does not invalidate ArgoCD's cached manifests, so already-committed overlays can stay inactive for up to 24 hours. Force a refresh:

```bash
kubectl -n argocd patch app envoy-gateway --type merge \
  -p '{"metadata":{"annotations":{"argocd.argoproj.io/refresh":"hard"}}}'
```

**Is the key right?** A key the chart does not recognize is accepted and ignored. Compare your key path against `base.yaml` and the chart's documentation.

## Remove an overlay

Delete the file, commit, and push. The value reverts to whatever `base.yaml` specifies.

```bash
git rm values/envoy-gateway/overlays/30-replicas.yaml
git commit -m "Revert Envoy Gateway replica override"
git push
```

## Migrating hand-edited manifests

If you previously edited a file under `apps/` to change Helm values, move those changes into an overlay before your next `nic deploy --regen-apps`, or they will be overwritten. Compare your edited copy against a freshly generated one, and move the values differences into `values/<app>/overlays/`.

Changes that are not Helm values, such as sync policy or destination, are not covered by overlays. Open an issue rather than hand-editing a generated manifest.

## For Software Pack authors

A pack is deployed _by_ ArgoCD and has no write access to the GitOps repository, so a pack cannot install its own overlay. If your pack needs a foundational component configured a particular way, document the overlay file an operator should commit, including the numeric prefix you expect, so operators can reason about precedence against other packs.

See [Build your own Software Pack](/docs/software-packs/build-your-own) for the rest of the pack authoring workflow.
