<section class="nebari-section nebari-compare" aria-labelledby="what-you-dont-have-to-do">
  <h2 id="what-you-dont-have-to-do">What you don't have to do</h2>
  <p class="nebari-section__subtitle">Nebari runs the layer underneath your apps, so your team doesn't have to.</p>

  <div class="nbr-table-scroll">
    <table>
      <caption class="sr-only">What each task takes without Nebari, and what the platform does instead</caption>
      <thead>
        <tr>
          <th scope="col">Task</th>
          <th scope="col">Without Nebari</th>
          <th scope="col">With Nebari</th>
        </tr>
      </thead>
      <tbody>
        <tr data-draw>
          <th scope="row">Deploying an internal app</th>
          <td data-label="Without Nebari"><span class="nebari-chore">Repeat the same routing, login, and HTTPS setup for every service you deploy.</span></td>
          <td data-label="With Nebari">
            Everything that makes it a shared app comes with it: an address, HTTPS, the platform login, and a tile on the landing page.
            <a href="/docs/explanations/software-packs/">How packs work</a>
          </td>
        </tr>
        <tr data-draw>
          <th scope="row">Setting up sign-in for a new app</th>
          <td data-label="Without Nebari"><span class="nebari-chore">Ask an admin to add every new app to your company's login system, and wait.</span></td>
          <td data-label="With Nebari">
            Sign-in comes with the app. What's left for you is deciding who gets in, by group or role, rather than wiring up the login itself.
            <a href="/docs/how-tos/keycloak-auth/">Set up single sign-on</a>
          </td>
        </tr>
        <tr data-draw>
          <th scope="row">Tracking infrastructure config</th>
          <td data-label="Without Nebari"><span class="nebari-chore">Keep configuration in sync across environments manually.</span></td>
          <td data-label="With Nebari">
            Every environment is built from the same git repository, and the platform keeps each cluster's setup matching it.
            <a href="/docs/explanations/nkp-architecture/#gitops-via-argocd">GitOps on Nebari</a>
          </td>
        </tr>
        <tr data-draw>
          <th scope="row">Watching what your apps are doing</th>
          <td data-label="Without Nebari"><span class="nebari-chore">Build and run your own pipeline for logs, metrics, and traces.</span></td>
          <td data-label="With Nebari">
            Your apps send logs, metrics, and traces to the platform, and it passes them to the monitoring system you already use.
            <a href="https://packs.nebari.dev/lgtm-pack/">LGTM monitoring pack</a>
          </td>
        </tr>
        <tr data-draw>
          <th scope="row">Giving your team access to an LLM</th>
          <td data-label="Without Nebari"><span class="nebari-chore">Build your own access rules, usage limits, and API keys around the model server.</span></td>
          <td data-label="With Nebari">
            They come with each model, so two teams can have separate keys and limits.
            <a href="https://packs.nebari.dev/llm-serving-pack/">LLM serving pack</a>
          </td>
        </tr>
      </tbody>
    </table>
  </div>
</section>

<section class="nebari-section nebari-section--muted nebari-principles" aria-labelledby="principles">
  <h2 id="principles">Development principles</h2>

  <ul class="nebari-principles__list not-content" role="list">
    <li>
      <h3>Open source</h3>
      <p>All projects are developed under an open source license, and built using open source software.</p>
    </li>
    <li>
      <h3>Community-oriented</h3>
      <p>All projects welcome community contributions and engagement in project spaces and community meetings.</p>
    </li>
    <li>
      <h3>Composable architecture</h3>
      <p>All projects have a modular design and integrate with each other, while also allowing for independent use and extensibility.</p>
    </li>
  </ul>
</section>
